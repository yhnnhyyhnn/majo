## 1. 背景与目标（待细化）

Memory 负责跨 Session 的知识沉淀——学习用户偏好、项目约定，避免每次新 Session 都从零开始理解上下文。这是 [PRD P1-3](../01-Product/PRD.md) 范围的能力，v1.0 不强制交付，但需要在 Context Engine（[RFC-0002 §5](RFC-0002%20Context%20Engine.md#5-检索结果融合与-reranking)"用户历史交互"权重维度）中预留接口。

## 2. 本RFC需要回答的核心设计问题

1. Memory 存储的内容边界是什么——用户偏好（代码风格、常用工具选择）、项目约定（命名规范、架构模式），还是也包括具体任务的历史决策？
2. Memory 的写入时机是显式的（用户主动"记住这个"）还是隐式的（系统从行为模式中自动提炼）？隐式提炼的准确性如何保证？
3. Memory 是否需要遗忘机制（过时的偏好/约定如何被覆盖或淘汰）？
4. 跨项目的 Memory 共享边界如何划分——用户级别偏好可跨项目复用，但项目约定显然不能跨项目污染
5. Memory 检索时如何避免"过度个性化"导致 Agent 行为变得不可预测（呼应 [Product Philosophy](../00-Vision/Product%20Philosophy.md) 可解释性支柱，Memory 的使用也应可审查）？
6. 团队场景下，Memory 是否需要支持团队级共享（例如团队统一的代码规范约定），如何处理个人偏好与团队约定的冲突？

## 3. 建议章节结构

- 核心概念（用户偏好/项目约定/记忆条目的分类体系）
- 写入策略（显式 vs 隐式）
- 存储与检索接口
- 与 Context Engine 的集成方式
- 遗忘与更新机制
- 可审查性设计（用户可查看/编辑/删除记忆条目）
- 风险与缓解
- 验收标准
- 开放问题

## 4. 已知的关键设计张力

- **自动学习 vs 可预测性**：Memory 自动学习能减少用户重复解释的负担，但过度依赖隐式学习会让 Agent 行为变得难以预测，与"可解释性优先"的哲学存在张力
- **个人记忆 vs 团队一致性**：个人偏好优化了单人效率，但团队协作场景下不一致的 Agent 行为可能造成代码风格混乱

## 5. 前置依赖

- [RFC-0002 Context Engine](RFC-0002%20Context%20Engine.md) 需先确定 Memory 接口的具体形态（§8 提到的"用户历史交互权重"）
- 需要先有真实用户使用数据，才能验证"隐式学习"策略的可行性，建议 v1.0 先做显式记忆（用户主动标注），隐式学习留待后续验证
