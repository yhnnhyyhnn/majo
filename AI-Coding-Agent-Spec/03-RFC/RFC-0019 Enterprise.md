## 1. 背景与目标（待细化）

**本 RFC 仅做架构预留讨论，不构成 v1.0 交付范围。** 企业级能力（RBAC、审计日志、私有化部署、合规）是 [PRD.md](../01-Product/PRD.md) 明确排除在 v1.0 之外的 P2 能力，服务于 [Mission.md](../00-Vision/Mission.md) 定义的"先对标个人/团队核心能力"策略。本 RFC 的价值在于识别哪些 v1.0 的底层设计决策会显著影响未来企业化的难度，避免技术债务积累到无法挽回。

## 2. 本RFC需要回答的核心设计问题

1. RBAC（基于角色的权限控制）与 v1.0 的 Permission 系统（[RFC-0015](RFC-0015%20Permission.md)，面向个人自主性配置）在设计理念上有何本质差异，v1.0 的设计是否需要为未来 RBAC 扩展预留字段/接口？
2. 审计日志的企业级要求（不可篡改、合规留存周期）与 v1.0 的 Telemetry（[RFC-0016](RFC-0016%20Telemetry.md)，面向个人调试）设计目标冲突之处在哪里？
3. 私有化部署（客户自己的基础设施内运行，不依赖任何外部云端服务）对模型 Provider 接入（[RFC-0012 Model Router](RFC-0012%20Model%20Router.md)）提出了什么约束（必须支持完全离线的本地模型）？
4. 团队级 Memory/Knowledge 共享（对应 [RFC-0005](RFC-0005%20Memory.md)、[RFC-0017](RFC-0017%20Knowledge.md)）在企业多用户场景下的数据隔离要求是什么？
5. SSO/统一身份认证的接入是否需要独立的用户身份模型，v1.0 单用户本地场景是否需要为此预留身份抽象层？

## 3. 建议章节结构

- 背景：为什么 v1.0 不做，未来做的触发条件（团队规模/客户需求信号）
- RBAC 模型设计（未来）
- 审计日志企业级要求 vs v1.0 Telemetry 的差异分析
- 私有化部署约束对现有 RFC 的影响评估
- 团队级数据隔离设计（未来）
- v1.0 应预留的最小接口点清单
- 明确的非目标（v1.0）
- 开放问题

## 4. 已知的关键设计张力

- **过早预留 vs 技术债务**：完全不考虑企业化可能导致未来大规模重构；过度预留又违背"先做扎实核心能力"的现阶段使命，需要精确识别"哪些是低成本预留、哪些是真正的过度设计"
- **本地优先哲学 vs 企业私有化部署需求**：两者方向看似一致（都强调不依赖强制云端），但企业场景的"私有化部署"通常还要求更严格的多用户隔离、集中管控，这与"个人本地工具"的默认假设存在设计张力

## 5. 前置依赖

- 需要 v1.0 Permission（RFC-0015）和 Telemetry（RFC-0016）先完整落地，才能准确评估企业化扩展的接口缺口
- 需要真实的企业客户需求信号（而非假设）才应该启动详细设计，避免自我想象的过度设计
