# Mission

## 现阶段使命

**在 12-18 个月内，做出一个功能对标 Cursor / Claude Code / OpenCode 核心能力的 AI Coding Agent 产品，验证团队有能力做出行业主流水准的 Agent 产品，再谈差异化。**

## 为什么先对标、不先做差异化

这是本规范一个明确的、经过讨论确认的策略选择，原因：

1. **核心能力还没有捷径**。Agent Runtime、Context Engine、Tool Runtime 这些底层能力，Cursor/Claude Code/OpenCode 已经用真实用户反馈打磨了 1-2 年。跳过对标直接做差异化，大概率是在没有把地基打好的情况下盖装饰。
2. **差异化需要用户基数和反馈validate**。没有一个能打的基础产品，差异化功能没有用户量来验证是否真的有价值。
3. **对标本身就是一个可衡量的里程碑**。相比"做出差异化"这种模糊目标，"核心功能对标 X"是可验证、可拆解、可排期的。

## 对标范围：什么叫"功能对标"

参考 [PRD.md](../01-Product/PRD.md) 的详细范围，这里给出使命层面的边界：

### 必须对标的核心能力（P0）

| 能力域 | 对标对象 | 验收标准 |
|---|---|---|
| Agentic 循环（规划-执行-观察-反思） | Claude Code / OpenCode | 能自主完成多步骤任务，无需每步人工干预 |
| 代码库上下文理解 | Cursor（Codebase Indexing） | 能基于自然语言描述定位相关代码，而非仅靠已打开文件 |
| 工具调用（文件读写/命令执行/搜索） | 三者通用 | 工具集覆盖率与 Claude Code 持平 |
| 多文件协同编辑 | Cursor（Composer） | 能在一次任务中一致地修改多个相关文件 |
| Diff 预览与人工确认 | 三者通用 | 修改前展示 diff，用户可逐项接受/拒绝 |
| Session 与上下文持久化 | OpenCode | 可恢复历史会话，上下文不丢失 |
| 权限与沙箱执行 | OpenHands（Sandbox 隔离） | 命令执行有明确权限边界，不会失控 |
| MCP 协议接入 | Claude Code / OpenCode | 支持接入外部 MCP Server 扩展工具集 |

### 明确不在本阶段范围内（P2+，留待差异化阶段）

- 云端全自动 issue-to-PR 工作流（Codex/OpenHands 的重型场景）
- 团队协作/多人实时协同编辑
- 自定义模型微调/私有模型训练闭环
- 企业级 RBAC、审计等（见 [06-Enterprise](../06-Enterprise/_INDEX.md)，先占位后落地）

## 阶段性目标（里程碑）

具体路线图见 [Roadmap.md](../01-Product/Roadmap.md)（当前为大纲，待后续补全）。使命层面只锁定三个阶段性检验点：

1. **M1 - 可用的 Agentic Loop**：CLI 工具能完成"读需求→改代码→跑测试→报告结果"的完整闭环。
2. **M2 - 深度上下文 + IDE 集成**：达到 Cursor 级别的代码库索引和编辑器内交互体验。
3. **M3 - 生态可扩展**：MCP 支持成熟，第三方可以为产品扩展工具能力。

## 使命的检验方式

不用"感觉做得不错"作为验收标准。每个 P0 能力都应该有可执行的验证方式（真实任务、真实代码库、可复现的测试集），这一点在 [Design Principles](Design%20Principles.md) 中进一步展开。
