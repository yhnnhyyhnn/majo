# Product Philosophy

## 核心信条

**Agent 是放大器，不是替代者。人始终是任务的最终负责人。**

这不是营销话术，是贯穿本规范所有架构决策的约束。每当 Agent Runtime、Permission、Review 等子系统的设计出现"要不要让 Agent 自己决定"的分歧时，回到这条信条做判断。

## 四个哲学支柱

### 1. 人在回路（Human-in-the-Loop），默认开启

Agent 的每一个有副作用的动作（写文件、执行命令、提交代码）默认都应该是**可观察、可中断、可撤销**的。这不代表用户必须逐步确认每一步——而是代表：

- 用户可以选择自主性级别（见 [Design Principles](Design%20Principles.md) 的"渐进自主性"原则）
- 无论选择哪个级别，用户永远能看到 Agent"打算做什么"和"已经做了什么"
- 任何时候用户都可以打断、回退

对应的架构落地在 [RFC-0015 Permission](../03-RFC/RFC-0015%20Permission.md)（大纲）和 [RFC-0001 Agent Runtime](../03-RFC/RFC-0001%20Agent%20Runtime.md) 的执行循环设计中。

### 2. 可解释性优先于"魔法感"

很多 AI 产品追求"看起来很智能"的惊艚感。我们的取舍相反：**宁可让用户觉得"这个 Agent 很朴实但我理解它在干嘛"，也不要"这个 Agent 很神奇但我不知道它做了什么"。**

具体体现：
- Agent 的每一步推理和工具调用都应该有可读的日志/展示，而不是黑盒执行后直接甩结果
- 上下文注入的内容应该是可审查的（用户能看到"Agent 这次参考了哪些文件"）
- 拒绝"过度包装"的进度提示（如虚假的百分比进度条），用真实的执行状态

### 3. 失败要显性、要可恢复

Agent 会犯错——这是给定前提，不是要消除的异常。哲学上我们不追求"让 Agent 永不犯错"，而追求：

- 犯错时用户能第一时间知道（而不是发现代码库已经被改坏了才知道）
- 犯错的代价可控（sandbox、diff 预览、git 集成让"撤销"永远可行）
- 犯错后系统能从中学习调整（见 [RFC-0005 Memory](../03-RFC/RFC-0005%20Memory.md) 大纲）

### 4. 本地优先，云端增强

开发者的代码是最敏感的资产之一。哲学立场：**默认本地执行、本地存储，云端能力是可选的增强，不是强制依赖。**

这直接影响架构：Workspace、Sandbox、Tool Runtime 默认在本地进程/本地容器中运行；Cloud Agent（[RFC-0011](../03-RFC/RFC-0011%20Cloud%20Agent.md)）是独立可选模块，用于处理长耗时/离线任务，而不是产品的必经路径。

## 哲学与商业化的取舍

当"更快对齐商业指标"和"以上四条哲学"冲突时的处理原则：

- 短期功能开发可以为了对标竞品做取舍（例如某个自主性级别的 UI 细节参考 Cursor）
- 但四个支柱本身不因为商业压力而妥协——例如不会为了"看起来更智能"而牺牲可解释性
- 任何试图打破这些原则的功能提案，需要在 [08-ADR](../08-ADR/_INDEX.md) 中明确记录理由，而不能悄悄绕过
