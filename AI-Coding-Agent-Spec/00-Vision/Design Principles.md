# Design Principles

十条设计原则，作为 PRD、Architecture、RFC 撰写与评审时的检查清单。每条原则给出**原则本身**、**为什么**、**违反时的信号**。

## 1. 渐进自主性（Progressive Autonomy）

**原则**：自主性是一个可调节的梯度（只读建议 → 需确认执行 → 自主执行+事后报告），不是开/关二元开关。

**为什么**：不同任务、不同用户信任阶段需要的自主程度不同。新用户第一次用需要逐步确认建立信任；熟练用户跑重复性任务需要"扔给它跑完再看"。

**违反信号**：产品只有"全自动"或"全手动"两种模式，或自主性级别在会话中不可动态调整。

## 2. 上下文相关性优先于上下文数量

**原则**：Context Engine 的目标是"注入最相关的最少上下文"，不是"塞入尽可能多的代码"。

**为什么**：LLM 上下文窗口有限且注意力会被稀释；不相关上下文会降低输出质量并增加成本。

**违反信号**：Context Engine 设计中出现"把整个文件/整个目录都丢进去"这类简化方案作为默认策略。

## 3. 每个动作可追溯

**原则**：Agent 执行的每个工具调用都应记录：为什么调用（推理片段）、调用了什么（参数）、结果是什么。

**为什么**：支撑 [Product Philosophy](Product%20Philosophy.md) 的可解释性支柱，也是调试 Agent 行为问题的必要条件。

**违反信号**：Telemetry/日志设计中工具调用没有关联的推理上下文，只有"调用了 X 工具"这种孤立事件。

## 4. 破坏性操作前置确认，非破坏性操作可自动执行

**原则**：读取类、只读分析类操作可以无需确认自动执行；写文件、执行命令、git 操作等有副作用的操作，其确认策略由自主性级别决定，但"删除"类操作永远需要更高确认门槛。

**为什么**：平衡效率与安全，不能让用户为了"看一眼文件"也要点确认，也不能让"rm -rf"式操作在低信任阶段被静默执行。

**违反信号**：Permission 系统对所有工具调用一视同仁，没有按操作风险分级。

## 5. Diff 优先于覆盖

**原则**：任何文件修改都应该以 diff 形式呈现并可逐块（hunk-level）接受/拒绝，而不是整体覆盖文件。

**为什么**：保留用户对代码的最终控制权，降低"Agent 改坏了我没注意到的部分"的风险。

**违反信号**：编辑工具设计中只有"写入整个文件"这一种原语，没有基于 diff/patch 的细粒度接口。

## 6. 沙箱是缺省，不是选配

**原则**：命令执行、危险工具调用默认在隔离环境（进程级/容器级）中运行，用户需要显式提升权限才能让 Agent 直接操作宿主环境。

**为什么**：编码 Agent 天然需要执行任意命令（跑测试、装依赖），这是最大的安全风险面。

**违反信号**：本地 CLI 模式下命令执行直接调用宿主 shell，没有资源/文件系统边界。

## 7. 失败是一等公民状态，不是异常

**原则**：Agent 执行流程的状态机必须显式建模"失败"和"部分完成"状态，并给出清晰的恢复路径，而不是把失败当成需要 try-catch 掩盖的意外。

**为什么**：呼应 [Product Philosophy](Product%20Philosophy.md) 的"失败要显性、要可恢复"。

**违反信号**：Task Engine 的状态机只有 pending/running/done，没有 failed/partial 及对应的恢复动作。

## 8. Provider 无关，模型可替换

**原则**：Agent Runtime、Prompt Engine 的设计不应该硬编码某个特定 LLM Provider 的 API 形态，模型层要能替换（不同厂商、不同版本）。

**为什么**：模型迭代速度极快，产品的核心价值应该在 Agent 编排层，不能被单一模型供应商绑定。

**违反信号**：工具调用格式、prompt 模板直接耦合某厂商 SDK 的专有字段，切换 Provider 需要重写核心逻辑。

## 9. 工具集可扩展，协议优先于硬编码

**原则**：新增 Agent 能力优先通过标准协议（如 MCP）接入，而不是在核心代码里硬编码新工具。

**为什么**：支撑生态可扩展性（见 [Vision](Vision.md) 五年愿景），避免核心代码库随工具数量线性膨胀到不可维护。

**违反信号**：每加一个新工具都需要修改 Agent Runtime 核心调度逻辑。

## 10. 可验证优先于"感觉好用"

**原则**：新增能力的验收标准必须是可执行、可复现的（真实任务集、自动化测试），主观的"用起来顺手"不能作为唯一验收依据。

**为什么**：呼应 [Mission](Mission.md) 的"使命的检验方式"，避免团队在没有客观反馈的情况下自我感觉良好。

**违反信号**：PRD 或 RFC 的验收标准写成"用户体验良好""交互流畅"这类不可执行的描述，没有对应的测试集或指标。
